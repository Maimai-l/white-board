# 测试里的固定等待改成等条件

状态：完成　　来源：流程改进

## 为什么

测试里约有 77 处固定等待（`wait_for_timeout`、`sleep`），集中在 `tests/e2e/test_shell_input.py` 等文件。
固定等待让测试变慢，机器忙时又容易时好时坏。

## 要做什么

- 逐个看：能等页面状态的改成 `wait_for_function` / `expect`；确实要等一段时间的（比如测「停顿半秒」）保留并写明原因。

## 验收

- `make e2e` 用时下降，连跑 5 次全部通过。

## 进展

- 2026-11-20 `claude/test-waits`：`tests/` 下 64 处固定等待（`wait_for_timeout`、`time.sleep`、
  `asyncio.sleep`）逐个看过。
  - 50 处改成等条件。能看页面就看页面：工具盘的 CSS 过渡走完（`getAnimations()`）、文件夹亮起、
    空位让开、卡片落回、速写画面左右两半都有墨、剪贴板里有图；其次是同步状态：两端 `lastSeq`
    对齐（`wait_seq`）、待发队列清空、手掌屏蔽结束（`penActive()`）、本机缓存写进去了、
    服务端看见断开（`detached` 事件）、后台线程跑完（`threading.Event` / `join`）。
  - 4 处是「什么都不该发生」的反向检查（视图不被拉回、慢拖没有惯性、不吸附），改成数渲染帧：
    应用是按帧动的，等十帧比等几百毫秒说得清。
  - 10 处保留按时间等，都写明了原因：松手前停住、超过 VELOCITY_WINDOW_MS（2 处，`hold_still`）、
    外壳断流 SHELL_STALL_MS（2 处），常量从应用源码里读（`app_constant`），按页面自己的时钟等
    （`wait_page_ms`），不用猜余量；手移动的节奏（2 处）；速写宽限期到点也不能结束（3 处，
    `outlast_grace`）；插件没有后台页、加载完没有事件可等，隔 250 ms 重试（1 处）。
  - `test_flick_keeps_scrolling_with_momentum` 时好时坏的原因：惯性按帧衰减，每帧最多按 32 ms
    算，机器一忙帧变少，滑完要的时间比写死的 1.3 秒长；「松手时的位置」又是另一次调用才量的。
    现在松手和之后的几帧在同一次调用里量，「停下来」改成连着 5 帧不动。
  - `test_cache_writes_never_land_on_a_stroke` 原来等 1.2 秒，对的是老实现的写盘时刻；现在防抖
    是 4 秒，第二笔根本碰不上写盘，把「书写中让开」的判断删掉它照样通过。改成第二笔一直写到
    写盘到点为止，删掉判断就失败。这一条因此多花约 2.5 秒。
  - 页面里用 JS 计时的等待也顺手改了三处：手指拖卡片停在落点（2 处）、擦除用例等推迟的回执。
    长按时长、动画正中间取值、合成手势的节奏是真的在量时间，没动。
- `pytest tests/e2e -q`（本机 4 核，Chromium 1255）：改之前 189.4 秒；改之后连跑 5 次全部通过，
  181.0 / 181.3 / 181.9 / 182.8 / 184.3 秒。省得不多：e2e 的时间主要花在每个用例开页面、
  起服务端上，固定等待合起来只有十几秒。
- WebKit 本机没有，`make webkit` 没跑，要看 CI 的 webkit job（其中几条用到了 `penActive()`、
  IndexedDB 轮询）。
- 遗留：在 4～8 个满载 CPU 的压力下，`test_a_new_folder_can_be_named_on_the_ipad`（没改过）偶尔
  等不到起名框，dev 上同样会（15 次里 1 次）：失败截图里新建对话框没开着。正常负载下没出现过。
